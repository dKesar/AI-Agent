# Практика 3. Ошибки, уточнение и собственный случай — 45 минут

[Предыдущая](developer_tools.md) · [Следующая](04_defense.md)

Дополнительный маршрут для подготовленной группы. Основное задание без автотестов — [здесь](03_controls.md).

**Цель:** проверить границы исполнения и добавить проверяемое расширение. Файлы для изменения: [policies.json](../data/policies.json) и новый `tests/test_my_case.py`. Не отключайте проверки в ядре ради прохождения тестов.

| Минуты | Действие |
|---|---|
| 0–10 | Предсказать и проверить пять проблемных случаев |
| 10–20 | Уточнить неоднозначный запрос новым запуском |
| 20–35 | Добавить регламент и два собственных теста |
| 35–45 | Заполнить отчёт и паспорт кейса |

```bash
python -m agent_lab --case missing
python -m agent_lab --case unknown
python -m agent_lab --case tool_error
python -m agent_lab --case injection
python -m agent_lab --case normal --steps 1
```

В отчёте отличите нормальную передачу человеку от технической ошибки. Для `injection` объясните отдельно поведение симулятора и проверку исполнителя. Запустите:

```bash
python -m unittest tests.test_core.CoreTests.test_forbidden_action -v
```

Уточнение: выполните `ambiguous`, выберите одну задачу и создайте новый JSON с уточнённым `question`. Например, оставьте только восстановление доступа. Проверьте, что новый запуск получает `IT-02`. Это новый запуск, не продолжение сохранённой сессии.

## Расширение: регламент командировок

Добавьте запись `TR-01`, название «Командировка», ключ `командиров` и правило: «Для командировки укажите цель, даты, место и согласование руководителя». Это вымышленный учебный регламент. Не меняйте существующие ключи.

В `tests/test_my_case.py` напишите два теста через `unittest`:

1. Запрос «Как оформить командировку?» с `priority="normal"` даёт `awaiting_review`, содержит `TR-01` и `SLA-01`, `sent` равен `False`.
2. После поиска этого регламента и получения SLA попытка `prepare_draft` с `policy_id="HR-01"` поднимает `ToolError`.

Начните с копии структуры одного теста из [test_core.py](../tests/test_core.py), но используйте свой вход и ожидаемый результат. Проверьте тесты:

```bash
python -m unittest discover -s tests -v
```

**Критерий готовности:** проходят ваши два теста и все исходные; в отчёте есть пример уточнения и объяснение ограничения симулятора. Для проверки качества теста временно подставьте неверный ожидаемый источник — тест должен упасть. После эксперимента верните правильное ожидание.

Сильной группе: придумайте запрос с отрицанием или синонимом, который текущий поиск обрабатывает плохо. Зафиксируйте ограничение, не заявляя, что его уже исправили. Предложите измеримый способ сравнить улучшенный поиск с исходным.
